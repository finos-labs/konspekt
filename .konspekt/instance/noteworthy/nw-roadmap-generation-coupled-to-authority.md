# Noteworthy: ROADMAP.md is a graph projection, and its automation complexity is set by the accept-authority model

ROADMAP.md is a generated projection of the instance graph — goals and their
`decomposes` tasks — patterned on the pure, deterministic `visual/build/snapshot.mjs`
and reusing `loadInstance()` from `lib/conformance.mjs`. The committed file is
marked AUTOGENERATED and guarded by a conformance freshness gate that
regenerates and diffs it, failing validation when the committed copy is stale.
The graph stays the single source of truth; the markdown serves readers who do
not yet know konspekt. This keeps the roadmap a query over edges rather than a
hand-maintained stored list.

The decided approach builds the local generator plus the freshness gate first
and defers an auto-commit workflow to a later step.

The shape and complexity of that later automation is determined directly by how
the roadmap is created and approved:

- an individual contributor with accept authority permits the simplest trigger —
  regenerate-and-commit on push-to-main, matching the notifier;
- a designated approver or a group requiring consensus means regeneration must
  route through whoever holds accept authority, so an unattended push-to-main
  auto-commit is insufficient and the automation grows more complex.

This is the same accept-authority configuration named by
[[task-persona-change-gate]]: the roadmap automation cannot be specified until
that model is fixed for the instance.
