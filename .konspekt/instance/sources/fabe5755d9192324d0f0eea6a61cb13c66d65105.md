# Source excerpt — push mechanism out of the store layer

Verbatim spans from the design conversation of 2026-09-14, both sides, with
elisions marked `[…]`. Selected, never paraphrased.

---

**Human:** I mean push out of the store layer

**Assistant:** My recommendation is that it is not required. Make the cursor plus changes-since the normative path, and treat a subscription as an optional accelerator a backend may offer. Every backend can satisfy polling, and a page polling a local server every second or two is indistinguishable from push at human timescales. Requiring a push channel would exclude backends that have no change feed and would put liveness into the conformance surface, where it does not belong. […] Git locally is a filesystem watcher on the instance directory […] Git remotely has no push at all unless something calls out: a webhook needs a public endpoint, and an Action can fire one […] Mongo has change streams with resume tokens, which line up exactly with the cursor. Postgres has two levels: `LISTEN`/`NOTIFY` fired by a trigger, which is easy and drops events if nobody is listening, and logical decoding, which is durable and replayable and costs a replication slot. One rule makes all of them interchangeable: the notification carries the cursor and nothing else. […] The last hop is separate from all of this. Whatever the backend does, the view is a browser page, so the local server pushes to it over server-sent events […]

**Human:** right. are you saying we don't need to mandate actual push and just assume that between client pull and backend push there will always be a way for the UI to get an update?

**Assistant:** Close, but the load isn't on an assumption. Polling always works because the interface already requires the two things it needs: an opaque cursor and a changes-since query. Those are mandatory. Push is optional and buys latency only. So the correct framing is a mandated floor with an optional fast path. […] Changes-since must stay cheap and mandatory. If a backend can only answer it by scanning the whole store, polling degrades badly and push stops being an optimization and becomes a requirement. That is a real conformance bar for the interface: ordered, resumable, bounded work per call. And freshness is a different problem from delivery on the git backend. Polling the working tree tells you nothing about commits sitting on the remote. Somebody has to fetch.

**Human:** ok them. make a note of this for now. let's commit/push/PR and close the branch out.
