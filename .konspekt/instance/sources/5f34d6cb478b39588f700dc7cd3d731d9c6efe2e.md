Denis: let's talk about fleet of agents implementation now ... in terms of #1 - yes, let's start with git. One of the questions we want to sort out is how many local branches (one per agent?) are we going for, and how do we sync the local graphs. Or do we assume N agents hitting the same repo?

Claude: The branch question is downstream of the integration model. Serialized single-writer committer: agents are proposal producers, not git committers. Each agent generates a proposal and hands it to one committer that appends to a single proposed branch in arrival order, with rebase-append on residual contention. No per-agent branches and no per-agent local graph to reconcile. There is one graph; agents read it and write to it through the queue. This decouples the edges.md shard from fleet: fleet concurrency does not require the shard if the committer is serialized; the shard's real payoff is traversal cost (task-edge-traversal-layout).

Denis: serialized single-writer - logically could mean two things: all agents, operating in local branches, are writing to a local konspekt repo via a "konspekt-master" agent/mcp. Or it could mean they actually work off the same local branch and append serially.

Claude: Three readings. A: agents hold their own git branches and a master integrates by merge/rebase — that is per-agent branches with a broker, the conflict path and shard precondition return. B (target): agents never touch canonical git; each produces a proposal payload (excerpt, entity, edge rows, origin tag) handed to a single committer that appends to proposed in arrival order; one graph, agents only read it. C: agents share one branch behind a lock — every agent carries the full push discipline, a stalled lock stalls the fleet, no parallelism gained. Take B. Drop per-agent local branches. The committer is deterministic, not an LLM — an MCP server exposing konspekt_propose. Git authorship stays the human committer with the Signed-off-by trailer; which agent proposed lives in the graph as the origin tag.

Claude: A worktree per agent buys work isolation and does not conflict with B. A linked worktree binds to its own branch, so one worktree per agent means one branch per agent — but B holds as long as the committer never merges those branches. Treat each agent's branch as a durable outbox the committer reads, not a source it merges. The agent commits its proposal payload into its own worktree; the committer reads the payload files, orders them, and does the single canonical append itself. No local graphs to sync; sync is one-directional, outbox to committer to canonical. The gain over in-memory handoff is durability: an outbox commit survives a crashed agent and is inspectable.

Claude: Payload schema: proposals/<proposal-id>/proposal.md (frontmatter + entity body + edge rows) and source.md (verbatim, content-addressed). Frontmatter carries proposal_id, kind, origin (agent/model/session), scope (entity_type, atom_state), target, depends_on, source hash, optional claim. Origin cannot be spoofed: an agent writes only its own outbox branch, so the committer maps branch to agent and rejects mismatches. Scope is checked against grant, client-side, never gating the store. Committer protocol: read new proposal commits per outbox branch since last sequence; verify (recompute proposal_id and source hash, confirm origin equals branch owner, confirm scope, resolve depends_on); order by arrival adjusted for dependencies; fold into a durable proposed ref; the review assistant presents; the human names the subset per proposal marking inspection or batch; for each admitted proposal one atomic commit to canonical (source to sources/<hash>.md, entity file, edge rows into edges.md, an accept record) with hash-object verify, SHA recheck, DCO trailer; record admitted proposals accepted on the proposed ref, rest pending, nothing erased.
