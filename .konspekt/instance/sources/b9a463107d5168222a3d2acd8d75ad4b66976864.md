# Source excerpt — app design thread (konspekt UI application)

Verbatim spans from the design conversation of 2026-09-14, both sides, with
elisions marked `[…]`. Selected, never paraphrased.

---

**Human:** Let's talk about an app to help with the adoption goal. There should be a task open for the UI - find it. We're going to design in this thread

**Assistant:** Found it: `task-task-workthrough-ui` ("Work through and disposition tasks in the interface"), status open, review accepted, sitting under `goal-usability`. […] The three tasks describe one application, not three, and I would build it as one: a local-first single-page app served from the repo that reads the instance off disk, opens on a goal picker, drops into that goal's open-task queue, and puts the authority verbs on the task detail.

**Human:** We need to think about this differently. None of the existing LLM interfaces (web consoles, windows apps or IDEs) allow us to embed the UI. Therefore, sadly, we will have to run our app in parallel to the interactive LLM interface. We can have a listener that'll take care of picking up atoms written in and update the UI. We would need an API (not sure if one exist) to get LLM to accept prompts or signals to read atoms and state changes from the store

**Assistant:** One correction to the premise before the design, because it changes the shape of the app. Embedding is possible now. MCP Apps (SEP-1865) has been final since January 26, 2026: a server predeclares an interface as a `ui://` resource, the host renders it in a sandboxed iframe, and the embedded page talks back over the same JSON-RPC as every other MCP message. […] On the reverse direction, your instinct is right and it is now a hard rule. SEP-2260 requires that `roots/list`, `sampling/createMessage` and `elicitation/create` be associated with an originating client-to-server request, and standalone server-initiated requests of those types must not be implemented. […] There is no inbound prompt API for claude.ai or ChatGPT web, and the protocol has closed the door on building one. A watcher cannot wake a chat session.

**Human:** right. we can't really drop native agent UI - it has too many features.

The native agent keeps conversation, tool calls, model work, and everything else you would have to rebuild badly. The app takes the things chat handles poorly: a queue of proposed atoms with their provenance side by side, the graph with status and review as visual channels, and batch disposition where you accept nine and reject one in a few seconds instead of nine turns. The instance stays the coordination point between them […]

**Human:** We are in the Claude mobile app now. Should distinguish between Claude mobile and konspekt mobile

**Assistant:** Claude mobile is a host surface, the same role as the web UI and the IntelliJ plugin. Two properties make it its own box. It cannot run local servers, so only remote MCP servers work there, and connectors cannot be added from the app itself […] Konspekt mobile is a renderer, the same role as the browser page and the iframe. It is your HTML UI at phone width, reached in the phone's browser against whatever endpoint serves it. It needs no host support at all, which is precisely why it is the safer remote answer.

**Human:** Don't see how claude mobile can be a target.

**Assistant:** Agreed. Even if the card renders, it is a transient artifact in a scrollback, sized for a phone, inside a host you cannot configure from the device. Nothing about that suits a review queue. […] review on the go means konspekt mobile in the phone browser, which is your code end to end and needs no host cooperation.

---

**Human:** I don't like this rule. Claude native should be able to write anything it writes today. The app should be able to write qs much as we can architect/enable it. We must think about the way to update claude native channel and we can make assumptions. One such assumption would be "if something updates the instance and claude season is not made aware then there could be a conflict"

**Assistant:** Fine, drop the scope split. The replacement is not permissions but versioning […] Make every write through the Konspekt R/W API a compare and swap: the caller passes the hash it read, and the API rejects the write if the atom has changed since, returning the current content so the caller can merge and retry in the same turn. […] That handles lost updates. It does not handle the agent working from a stale picture for a whole turn […] For that the store layer needs a cheap cursor, a commit SHA or sequence number, and a "what changed since" query over it. […] The failure to design against is the silent one: you accept an atom in the app, the agent later rewrites that node from its stale copy, and the accept quietly reverts to proposed with no error anywhere.

---

**Human:** 1. Per atom 2. What's your leaning 3. This needs to be a config option 4. Raises a flag in UI and requires and action 5. Explain this

**Assistant:** On 2, my leaning is an opaque cursor token returned by the store rather than a file in the instance. A cursor file is itself an atom that every write has to update, which makes it the one line every writer contends on, and it becomes a second source of truth that can disagree with the history. […] On 5, the difference is between two ways of writing to GitHub. A single-file update requires the file's current blob SHA, so if someone changed that file since you read it, the call fails. The multi-file push does not work that way. It reads the branch tip at the moment of the push, builds a new tree containing your file contents, and commits with that tip as parent. The ref update is a clean fast-forward and succeeds. The problem is that your file contents came from a read minutes earlier, so any change made to those files in between is replaced by your older version in a perfectly valid commit. No conflict, no error, no rejected push. […] One consequence of choosing per-atom granularity. The edge table is a single file, so two writers adding unrelated edges collide on it every time even though their rows are disjoint.

**Human:** Follow your leaning. Update the original diagram with two-way R/W on both sides. […] The next step will be UI embedding

**Assistant:** The line from the backend is tool calls: the model decides to call a konspekt tool, and the call executes from Anthropic's infrastructure over the connector. **Human:** let's now get deeper into the store layer. as I said, we need to make sure it is not just git, but arrows going into "working tree" and "github" remote make it very explicit. How about we add Mongo to it (as an enterprise backend) and change the diagram accordingly? Assuming Mongo is a good store, which I think it is - unless there's an performant scalable open source json document db

**Assistant:** It fits because every requirement maps to something native. Per-atom compare and swap is a conditional update matching the version field. Atomic multi-atom writes are multi-document transactions. The cursor you asked me to make opaque is a change stream resume token […] The problem is the licence. MongoDB moved to SSPL in 2018, which is not an OSI-approved open source licence […] The alternative I would lean toward is Postgres. JSONB gives you document storage with GIN indexing, transactions give you atomic multi-atom writes, `xmin` or an explicit version column gives you per-atom compare and swap, and logical decoding gives you a monotonic cursor. […] The footnote worth taking seriously is the third one. Git gives you history, attribution, and diff for free […] A database backend has to reproduce that explicitly with an append-only record of every write and who made it, or it loses the property the project is built on.

**Human:** 1. keep both; mongo for enterprise, postgres for open source. the rest of the questions is TBD. add the extended storage interface section (the interface + 3 backends) to the main diagram

**Assistant:** One thing the merged picture now shows that the separate diagrams did not. The two solid lanes reach inside the git backend, past the storage interface. On a Mongo or Postgres instance those lanes have nowhere to land, so an adopter on a database backend loses the git CLI and the GitHub connector entirely and has only the R/W API.
