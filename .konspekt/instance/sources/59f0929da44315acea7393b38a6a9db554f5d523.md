**Claude:** **task-multi-author-review — Support multiple human authors on one instance** Today one person proposes and accepts. Open the model to several people on the same instance without weakening propose→accept. Accept authority lives in config: a maintainers list in `project.md` names who can flip `review` to accepted, so the store stays read/write only and the authority does not move when the transport does. No proposer, human or machine, can accept its own or another's proposal — the maintainers list is the only source of the accept right. Concurrent writes to `edges.md` are the unsolved part: several authors pushing at once produce non-fast-forward conflicts on the single edge table, and retry covers two writers rather than a room of them. Success is two people proposing and one designated maintainer accepting on the same instance with no lost edges. **task-agent-fleet — One reviewer over a fleet of agents** Scale the current model to N agents proposing into one instance with a single human reviewer; the rule is unchanged and the work is making many concurrent machine proposers safe and legible. Provenance already carries `origin`; extend it so each proposal records which agent produced it […]. **task-enterprise-persistence — A durable store other than git** git is one backing store; some adopters need an enterprise database or object store with the same guarantees. Define a storage interface — read blob, atomic write of excerpt plus entity plus edges in one transaction, list, content-address — so git is one implementation and the enterprise store another […]. the source filename is currently the git blob SHA, and it moves to a SHA-256 over the verbatim excerpt […]. The store must expose a plain read path, not only an API, or it fails the manual-re-upload probe and becomes lock-in, and it adjudicates nothing — review stays in the conversation. **task-graph-analytics — Analytics and mining over the graph** Queries over nodes and edges that surface structure and history: edge density, provenance depth, proposal and acceptance counts, and the age of proposals that never landed. […] the capability is general and the research is its first consumer. **task-realtime-monitoring — Continuous monitoring of an instance** Run the analytics queries continuously and watch `review` transitions as they happen […]. The change source depends on the store […] so the detail here waits on `task-enterprise-persistence` settling the interface. **Claude:** **goal-collaboration — Share authorship across a team** Let several participants — people and agents — propose into and review one shared instance without weakening propose→accept, with accept authority named in config so it survives a change of backing store. Platforms build collaboration into their own closed state; the version that works across a neutral, portable record is the one no single vendor is incentivized to build. The hardest open part is concurrency control on the single edge table, unresolved and shared by both the human and the agent case. **goal-observability — Make the graph observable** Make the state and history of an instance legible through queries over the typed graph — edge density, provenance depth, proposal and acceptance counts, unaccepted-proposal age — run as projections outside the store and, at the limit, continuously. These measures are the same ones the effectiveness research needs, so the capability is general and the research is its first consumer. It runs entirely as regenerable projections and adds nothing back to the graph.
