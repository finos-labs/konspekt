Decision (2026-10-23): the fleet `setup` command must treat acceptance authority
as a blocking precondition, not a first-accept-time surprise.

Problem observed in the CDM adopter UAT (task-adopt-agent-fleet): a fleet was
stood up against an instance that declared no principals, so accepting a folded
proposal through the IntelliJ plugin wrote the transition with an empty `by` —
the acceptance lost its attribution and nothing failed at setup time. Declaring
principals makes the UI client fail-closed, but only once the human reaches the
accept step; the underlying gap is that an adopter can stand up a whole fleet
with no working acceptance authority at all.

Resolution: `setup` runs a read-only acceptance-authority preflight before
standing up any worktree and refuses when it fails. The preflight blocks on two
things. First, the canonical instance must declare an acceptance authority — a
human grantor principal and an effective accept grant. Second, KONSPEKT_PRINCIPAL
must be set in the environment and name a declared principal that holds an accept
grant. A new read-only `doctor` subcommand runs the same checks on demand from an
acceptance client's own shell. The env-var check validates the environment the
command runs in; a split topology still needs the export in each acceptance
client, and each client enforces fail-closed at accept time.
