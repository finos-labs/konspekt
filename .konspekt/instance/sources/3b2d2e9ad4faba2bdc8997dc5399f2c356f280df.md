From task-fleet-worktree-committer (accepted) — success criterion:

"Success is a committer that ingests proposals from N proposer outboxes,
verifies and orders them, folds the admitted subset onto canonical as proposed
with the human acceptor naming the subset, and leaves the store honest after a
crash between the fold commit and a `proposed`-ref update."

From docs/design/fleet-spec.md § Fold:

"Because canonical holds the payload, a crash between the fold commit and a
`proposed`-ref update cannot make the store lie: the ref is refreshed from
canonical, and canonical is never refreshed from the ref."

From implementations/fleet/app/proposed-ref.mjs (buildIndex / rebuildIndex
comments):

"Build the index by scanning canonical. Pure read: it joins the fold log to the
current `review` of each atom and classifies it. This IS the rebuild — there is
no incremental state to trust, so a fresh build after a crash is correct by
construction."

"Rebuild from canonical and overwrite the materialized index. The recovery entry
point: run after a crash, or whenever the cache is suspect. The result equals a
fresh buildIndex because canonical is the only input."

The invariant, the survivable crash points, and the rebuild procedure are stated
in three separate places (a task success line, one fleet-spec sentence, and code
comments) and nowhere assembled into a recovery contract an operator can follow.
