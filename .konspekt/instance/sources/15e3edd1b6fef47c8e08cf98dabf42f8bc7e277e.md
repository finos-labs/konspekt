Denis: a follow up on fleet design. I am thinking we can't really enforce the --worktree approach. We can use it as one of the implementaiton options, but to generalize, we should probably stick to one committer and have it accept proposals over MCP

Claude: ... What the per-agent worktree was actually doing is one job: carrying a proposal from a proposer to the committer. The outbox branch was the transport. So the generalization is to define the committer's proposal-ingest contract once — content-addressed, origin-tagged, persisted on receipt — and let any transport that satisfies it feed the single committer. Worktree-outbox satisfies it for co-located container agents. MCP satisfies it for anything that can call the committer, which covers the case the worktree can't: web and mobile conversations have no working tree, so the outbox mechanism doesn't exist there. MCP spans all of them, so it's the right general default, with the worktree kept as one conformant transport for the container case where it adds something. ... In the seed topology the conversation is the proposer and the persist-on-accept via the GitHub connector is the committer step fused into it — the n=1 case. The fleet separates the two roles, and MCP is how a proposer that isn't the committer reaches the one that is. ... The one thing MCP changes is where durability lives. With an outbox, a proposal is durable the moment the proposer commits it, before the committer reads it ... Over MCP the call is ephemeral, so durability moves to the committer: it has to persist each received proposal to the proposed ref before it acks ... "accept proposals over MCP" means the committer ingesting them into the queue. Acceptance authority — the konspekt review state — stays with you ... MCP carries proposals in; it holds no accept authority.

Denis: the proposers could commit and *then* make the MCP Call, though. could always rollback

Claude: Yes — commit-then-call composes the two cleanly. The commit gives proposer-side durability; the call gives reach. That settles the item-3 choice: a proposer with a writable store commits its content-addressed payload first, so the proposal survives a committer that's down or a call that fails, and the MCP call becomes the signal while the store holds the proposal. ... The call carries a pointer — the content hash or outbox ref. The committer fetches the bytes from the store it already trusts and hash-verifies on read, so the MCP channel never carries authoritative content. A compromised call can reference a hash; it can't forge one. ... Commit-first makes delivery idempotent. The payload identity is fixed before the call, so a timed-out retry resolves to the same hash and the committer dedups. That closes the lost-ack edge ... at-least-once delivery, exactly-once effect ... Rollback is clean up to the committer's persist-ack. Before the committer has folded the proposal into the proposed ref, the proposer's outbox commit is a private draft ... After the ack, the proposal is in the durable record, and retracting it is a state transition on the proposed ref — a withdrawn or tombstone terminal state, origin-tagged. ... A container proposer commits to its local outbox ... A web/mobile proposer has no local git, so its commit is a push to a remote outbox namespace via the connector, which means granting proposers write to `refs/konspekt/outbox/<agent-id>/*` under server-side protection that keeps canonical and proposed committer-only. ... commit-then-call gives proposers outbox-write; payload-in-call keeps them at zero repo write with durability resting entirely on committer persist-on-receive. For a proposer with no writable store at all, payload-in-call is the fallback.
